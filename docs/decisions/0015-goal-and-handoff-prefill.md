# 0015 会话目标（goal）与交接预填

日期：2026-11-13。状态：已接受。

## 背景

D22：交接质量取决于"任务是什么、下一步做什么"，但以前这两项全靠用户在交接对话框里手填。另一方面，任务会演变——开始只是普通聊天，跑了几十轮之后才值得定义目标，事前分类"这是不是目标任务"没有意义（普通聊天也可能演化）。方案见开发计划 §8 与 §12 D22。

## 决定

- **goal 是 Conversation 上的可空字段，不做任务分类。** 只在交接时被消费。推导链：显式 goal → 第一条用户消息（跳过 core 注入的 prompt）→ 标题。创建会话时可选填，运行中经 `conversation.configure` 随时改。
- **备用执行者**（`fallbackHarnessId`）同样存在会话上，指向一个与本会话当前负责人不同、且本构建有适配器的 harness。
- **`handoff.suggest` 是只读 RPC**：goal 按推导链得出；nextAction 从日志组装（有失败则写明失败原因 + 最近用户要求，再提醒核对工作目录）；接收方取备用执行者。全程零模型调用。
- 交接对话框打开前先取建议值预填，用户仍可全部修改；`prepare` 的既有前置条件（验证停止、接收方 ≠ 当前负责人）不变。
- **演变提醒用客观信号**：运行轮数 ≥ 5 且未设 goal 时，详情面板提示"定个目标"。不调用模型判断"需不需要目标"。
- 更新广播走既有 `conversation.updated`，多窗口天然同步；存储写失败与其它写入一样标 `StoreWriteError`（ADR 0012）。

## 后果

- 普通会话零负担：goal 为 null 时一切照旧，交接时用第一条消息兜底。
- 失败后的交接路径变成"点交接 → 表单已填好 → 确认"，但用户仍然过目——预填是默认值，不是自动决定。
- 备用执行者只是预填来源；不满足条件（同负责人、无适配器）时 `suggest` 返回 null，对话框退回默认选择。
